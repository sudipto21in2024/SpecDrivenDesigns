# Orchestration & Kilo Code Setup

## How to wire this pack into Kilo Code

1. **Load this whole folder as project rules/context.** Kilo Code supports custom modes and
   `.md` rule files — put this folder at the repo root (e.g. `/docs/agent-spec/`) so every mode
   can reference it via relative path.
2. **Create one Kilo Code custom mode per agent** in `01-agent-architecture.md`. For each mode,
   set its system prompt to: "You are the <Agent Name>. Read `/docs/agent-spec/01-agent-architecture.md`
   for your responsibilities and boundaries. Read `/docs/agent-spec/03-spec-driven-workflow.md`
   for the state machine. Only produce the artifact type listed for your role. Do not perform
   another agent's responsibilities."
3. **Restrict tool/file permissions per mode** where Kilo Code allows it:
   - Spec Agent: read/write only in `/specs/`
   - Architect Agent: read/write only in `/contracts/`, `/docs/adr/`, read-only elsewhere
   - Backend Agent: read/write only in `/src/backend/`, read-only on `/contracts/`
   - Frontend Agent: read/write only in `/src/frontend/`, read-only on `/contracts/`
   - Database Agent: read/write only in `/src/backend/.../Migrations/` and `04-database-schema.md`
   - QA Agent: read/write only in `/tests/e2e/`
   - Code Review Agent: read-only everywhere, write only to `/docs/reviews/`
   - DevOps Agent: read/write only in `/.github/workflows/`, deployment config
   - Documentation Agent: read/write only in `/docs/user-guide/`, `CHANGELOG.md`
   This mirrors "boundaries" in `01-agent-architecture.md` at the tooling level, not just prompt
   level — important since prompt-only boundaries get violated under pressure.
4. **Orchestrator mode drives the loop.** Its job each cycle:
   - Scan `/specs/**/*.md` front matter for tickets whose state has a defined next agent.
   - Dispatch that agent (in Kilo Code: trigger the corresponding mode/task with the ticket file
     as input).
   - On completion, re-read the ticket's updated front matter/state and decide the next hop per
     the state machine in `03-spec-driven-workflow.md`.
   - Write escalations to `/specs/escalations/` and pause that ticket when blocked.

## Suggested ticket batch order (bootstrapping the project)

Build foundational tickets before feature tickets so later agents have something to build on:

1. `LOGI-0000` — Repo scaffolding (solution structure, Vite app, CI skeleton) — Architect + DevOps
2. `LOGI-0001` — Warehouses CRUD (simplest entity, establishes patterns for all agents)
3. `LOGI-0002` — SLA rules (business rule reference doc, not code — Spec Agent only)
4. `LOGI-0003` — Auth & roles (Identity setup, JWT issuance, role middleware)
5. `LOGI-0004` — Vehicles CRUD
6. `LOGI-0005` — Drivers CRUD
7. `LOGI-0006` — Shipment status lifecycle (state machine on the entity)
8. `LOGI-0007` — Create shipment (see `09-sample-feature-spec.md`)
9. `LOGI-0008` — Edit/cancel shipment
10. `LOGI-0009` — Routes: create & assign vehicle/driver
11. `LOGI-0010` — Assign shipments to a route
12. `LOGI-0011` — Planning board (list/kanban view of shipments+routes)
13. `LOGI-0012` — Dashboard (counts, SLA breach flags)

Each of these becomes its own `/specs/features/<id>-<slug>.md` following the template in
`09-sample-feature-spec.md`, generated by the Spec Agent before any implementation starts.

## Guardrails against runaway autonomy

- **Hard stop on ambiguity**, not best-guess: see escalation rules in `03-spec-driven-workflow.md`.
- **Ticket-scoped diffs only** — Code Review Agent rejects any PR touching files outside the
  ticket's declared "downstream artifacts" section without a linked explanation.
- **No agent edits `contracts/v1-openapi.yaml` except the Architect Agent** — enforce via file
  permissions in step 3 above, not just instructions.
- **Human checkpoint at `SPEC_REVIEW`** for at least the first few tickets, until you trust the
  Spec Agent's acceptance criteria quality; can be relaxed later per ticket risk level.
- **CI is the final gate** — nothing merges on an agent's self-report of "done"; DevOps Agent's
  green pipeline is authoritative.

## Metrics to track once running

- Tickets completed per day, average cycle time per state (spot slow stages).
- % of tickets that hit `BUG_FOUND` (signal on spec quality or contract precision).
- % of tickets escalated to human (signal on ambiguity in your domain rules).
- Token/cost per ticket, broken down by agent (useful given the earlier Jira-token discussion —
  same discipline applies to every tool-heavy agent, not just a Jira integration).
